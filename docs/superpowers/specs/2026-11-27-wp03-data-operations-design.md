# WP03 / S3 — Data Operations: bounded synthetic design v0.1

Status: bounded design under approved Master Design v1.0 sections 4, 6–9 and S1 contracts; execution authorized when owner sends combined handoff prompt. No change of material architecture is authorized. Material schema/provenance/rollback/replacement/dependency/rights/deployment decisions outside this bounded design remain separate owner gates. This document records a proportionate six-cycle design review performed against current source and pinned research, not a claim of an installed skill or external builder review.

## Cycle 1 — Intent, scope, alternatives

Enable the user to safely prepare dirty bilingual terminology tables, understand loss/mapping and conflicts, preview additive changes, and approve a small atomic import using the same canonical gateway as manual edits. Provide a data-quality inspector and recovery readiness evidence. Input is synthetic only; actual personal/spreadsheet intake remains forbidden until G4 and rights/owner approval. First useful slice: strict local CSV/TSV + explicit mapping + reviewed canonical creation/link + export/backup/restore. Use one real accessible Data Operations workspace (dedicated route or integrated Exchange section; choose minimal navigation changes). No full spreadsheet editor, no CAT, no external AI/source ingestion, no S4/S5, no automatic translation.

Alternatives: embed OpenRefine/Anchovy (reject JVM/Electron/intermediate model and dependencies), new generic import database (reject schema drift), minimal local parser/staging (choose). Support narrow delimited text initially; Excel users can prepare CSV/TSV offline later; XLSX/DOCX/TBX/TMX/XML/legacy binary formats remain explicit deferred qualification, never mislabel as supported. JSON backup v1 stays separate empty-target restore, not an import shortcut. JSON presentation export is lossy and cannot restore canonical history. Optional staged interchange format is versioned *session-only* and not a backup; no arbitrary canonical JSON ingest.

## Cycle 2 — Architecture and semantics

UI -> application preparation/planning use cases -> pure domain validation -> existing gateway -> Dexie. Use separate immutable raw staging DTO with row ID, raw cells, row/line offsets, parse warnings, explicit mapping and mapping version, staged value, issue codes, user decisions, source file/session digest and base library revision. Never reuse row number or imported ID as canonical identity. Preserve Unicode, case, punctuation, missing values; optional exterior trim/redundant ordinary-space cleanup only as explicit before/after transform, no blanket NFKC/casefold/diacritic deletion. Mapped columns: one term text + language + role + optional external grouping key or explicit EN/TR mapping template. Require explicit mappings, missing role = unspecified if user selects policy; missing language = undetermined only with explicit policy; blank term invalid; missing translations never invented. No formula evaluation, HTML or Markdown execution. Headers not object prototypes; duplicate headers identified by positional index. Preserve raw only in memory; unsupported columns marked unmapped/loss report. Bilingual pairing/grouping is a user decision, not an inferred translation. Distinct same-surface concepts remain allowed; exact same text/language/role within a chosen concept may be skipped by explicit decision; same surface across concepts is ambiguous, not automatically merged.

Current schema: Concept, Expression, Provenance(kind manual/reviewed-candidate, source null or retained span), verified assertion, backup v1. Import uses only existing createConcept/addExpression ops, stable local IDs, local-user approval, base and expected revisions. Do not label imported entries reviewed-candidate without extraction source. For explicitly reviewed manually entered staged forms, existing manual provenance with source:null is the truthful v1 representation of the local user's approved entry; label the limitation: external row/file provenance is available in session preview/loss report only, not preserved as canonical source evidence. No scientific assertion or fabricated source. If durable import provenance is necessary for future real intake, it is a material migration decision, record G4 blocker; do not fake support. No change to v1 schema, backup envelope, op enum or protected field policy.

One bounded approved batch, all-or-nothing; no auto chunk commits. Proposal must preview actual operations, exact counts, digest and base rev; regenerate on source/mapping/selection/revision change, never reuse approval for changed payload. Multiple forms for newly created group must respect revision sequence (create first at rev0; addExpression expectedConceptRevision increments under gateway). Existing concept target explicit. ID collision fails closed. Same approved ID/digest replay no mutation; changed payload conflict; stale batch rebuild/review not retry. Backups precede apply, verified and explicitly offered/download acknowledged; no claim download persisted on disk. No blind destructive undo; use existing empty-target restore to separate empty context. Compensation/delete/merge and whole-library replacement need material design and safe migration; not enabled. Read-only maintenance offers issues and reviewed additive corrections, uses existing ordinary edit only where already supported via existing UI, not import update. No direct canonical writes or test-only bypass in production.

## Cycle 4 — Integrity/privacy and operational risk

Before enabling UI, enforce project-owned synthetic fixtures: immutable raw-byte SHA-256 allowlist or built-in exact fixture bytes (include downloadable dirty synthetic example; no unrestricted arbitrary file/paste activation in this gate). The pure parser/mapping functions accept arbitrary *synthetic test fixtures* in unit tests, not a product upload bypass. If a file picker exists, enforce pre-read byte bound and exact digest before staging, fatal UTF-8 and BOM policy; reject real/unknown uploads without canonical writes. No self-attested license/checkbox as sole gate. UI clear/reload/discard/source changes invalidate staging/approval; raw input never persisted, URL/log/server/network, backup or audit. Formula strings are inert; preserve exact data in raw and report risk; presentation export reuse existing CSV safety. Confirm counts, schema/identity, no verified edits, all-or-nothing, no orphaned rows, stale/abort/quota errors explicit, no in-memory fallback. Session report may be explicitly downloaded with privacy warning; not part of canonical backup.

G4 readiness is not just tests: stable actual origin, browser process restart/OS reboot, actual quota/eviction, realistic migration and blocked upgrade, isolated recovery, performance and rollback, source rights, owner sign-off. Native CI can establish synthetic probes, not target hardware acceptance. No fake schema v2 migration of production library; test isolated synthetic DB copy with representative additive migration and blocked upgrade; document limitations and avoid shipping migration. No real data, deployment, DB reset of user's existing library, or quota-filling on actual origin.

## Cycle 5 — Efficiency and delivery

Provisional conservative bounded synthetic intake (new internal limits, not an increase of existing extraction/backup limits): max 2 MiB file bytes pre/post-read, 200k UTF-16 decoded source, 1,000 data rows, 32 columns, 8,192 UTF-16 per cell, max 250 operations in one reviewed atomic ChangeSet. Header row excluded from data count, total row/cell/character limits checked during parse, explicit over-limit rejection before partial actionable stage, no truncation. If selected work exceeds op limit, refuse and let user explicitly choose smaller selection; no implicit partial application. Paginate staging/quality review (e.g. 50 rows) with complete counts, bounded issue lists, searchable filters, no missing issue or selection state across pages. Record rationale, exact measured sizes and fail-closed behavior. Reuse gateway and existing UI; no new runtime package, no schema migration, no broad refactor. Test deterministic operation complexity and actual browser at bounded scale, realistic library synthetic 10k/50k expressions subject to fixed backup size and runner resources; report closest valid workloads and blockers, no invented throughput promise.

## Cycle 6 — Challenge and reconciliation

Critical questions: Does a staged group accidentally imply equivalence? Are imported IDs or formula text executed? Can preview, backup or approval be stale? Does partial parse or duplicate create orphan records? Does canonical manual provenance falsely imply source evidence? Can batch replay regenerate IDs? Are actual cross-tab notifications promised? Can a user mistake presentation CSV for backup? Is a migration drill accidentally touching live DB? Acceptance tasks cover these. Use known gateway invariants instead of parallel implementation. Bounded decisions above are explicit; material deviations stop that subfeature and report, continue independent tasks. Use available Superpowers brainstorming/writing-plans/TDD/debugging/review/verification, no fabricated skill use or independent agents. The builder reconciles against actual code before changes, records any necessary decisions and executes plan in same assignment.
