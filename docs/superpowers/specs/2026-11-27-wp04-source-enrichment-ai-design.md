No claim that WP03 source was inspected at planning time. Builder must cross-check actual WP03 code before implementation. No material schema, network, rights or dependency authorization.

## Cycle 1 — Intent and alternatives

Provide a practical local workflow to find incomplete terminology records (e.g. a concept missing a Turkish or English expression), inspect source suggestions, prepare standardized task packets for optional external reviewers, receive structured responses, compare evidence and independent reviewer *claims*, and explicitly approve supported additive changes. External model/provider calls are not required. Alternatives: direct API client with keys/implicit source transfer (reject at current gates), embed external enrichment service (reject), local typed adapters plus user-mediated external review exchange (choose). Use synthetic fixtures only. No real source lookup, genuine model calls, real manuscripts/terminology, automatic verification, translations asserted true, or inference that a source identifier/license string proves rights. No WP05 phrasebank, TBX/TMX, writing or Turkish NLP changes.

## Cycle 2 — Architecture and contracts

Modular monolith, UI -> application use cases -> domain schemas -> narrow adapters; existing gateway/IndexedDB v1 remain authority. A SourceAdapter returns bounded session-only evidence suggestions tied to selected concept/expression IDs and record/library revision, explicit source ID/release/license/URI and fixture identity. Do not fetch URIs or render active untrusted content. Use immutable project-owned synthetic data and exact allowlisted fixture payloads (no unrestricted real uploads). Source registry distinguishes synthetic enabled and future real candidate disabled/conditional. Exact case/Unicode identity; language/role only explicitly mapped; same surface across concepts ambiguous, no automatic links. Source suggestion is not canonical proof; user review required.

External exchange uses separately versioned strict Zod DTOs, not canonical backup or ChangeSet. Suggested contracts (names may adapt to actual code, keep semantics):
- ReviewTaskPacket v1: format/version, taskId, taskDigest over immutable canonical JSON payload excluding digest, baseLibraryRevision, selected record IDs and revisions, taskKind, allowed operation/field scope, minimum necessary synthetic term text/language/role and explicitly selected context (default none), createdAt, response schema/instructions. No source manuscript, audit, unrelated records, credentials, URLs containing payload, internal hidden data, or automatic transmission. Explicit preview/consent and local file download only; no clipboard auto-send. User may manually give synthetic packet to external reviewer. Display example instructions with exact output format; synthetic fixtures/optional manual external service use not a proof of provider identity.
- ReviewResponse v1: format/version, taskId/taskDigest, reviewerSlotId, claimed provider/model/version (optional unknown clearly labeled), responseId, base revision and target IDs/revisions, scoped suggestions typed as proposeExpression or no-change/abstain, rationale and bounded evidence references; no arbitrary patch paths, executable text, ChangeSet, assertion, deletion, replacement, merge, canonical IDs for new expressions or embedded source text. Unknown keys, nonfinite, malicious prototypes, mismatched digest/task/record/revision/scope, duplicate slot/response and malformed schema fail closed. Canonical digest is integrity binding not signature/authentication. One response per preassigned slot; independent origin self-reported, cannot enforce actual blind independence. Separate slots, prompts omit other responses; no consensus by duplicates or copied slots. If real reviewer response not allowlisted, block activation under synthetic gate; provide built-in synthetic response bundles generated locally against current synthetic task and explicit simulated reviewer identities. A constrained user-selected external response flow can be demonstrated with fixtures bound to exact task; arbitrary upload not enabled until owner policy. Do not mistake generated simulation for actual LLM output.
- EvidenceCandidate is separate from ReviewVote: source/reference, quoted/exact fixture evidence where allowed, rationale, uncertainty/unsupported claim status; no invented bibliographic validation, evidence status and agreement shown separately. Exact equivalent suggestions grouped by target ID, text, language, role, operation; different text/case or concept stays separate, no semantic auto merge. Display reviewer count, eligible denominator, abstention, missing/invalid, disagreement; e.g. 3/3 means agreement of three accepted slots, not truth. No hidden confidence probability. No forced acceptance even unanimous.
- On user selection generate existing createConcept/addExpression only where actual supported workflow permits; prefer addExpression to explicitly selected existing concept with expected revision, existing immutable proposeChange/approveChange/applyChange and CAS, duplicate checks and before/after preview. No response-supplied canonical IDs, no new verification assertions, verified replacement, arbitrary edit, durable evidence fields or schema migration. Existing provenance manual/source:null only after explicit human review, clearly label that canonical v1 cannot retain external evidence or model provenance; session evidence report downloadable with explicit consent, not canonical backup. User approval of an expression does not validate scientific truth. No destructive ops, no bypass of WP03 bounds or protected fields.

Task packet and response data session-only (memory); reload/clear/new task/selection/source/revision invalidates stale approval, no persistence of raw response, prompts, unapproved suggestions, source or API data in storage/log/network/URL/audit/backup. Only approved canonical term text and existing manual metadata persist. Use actual async guards; stale proposal fail closed and refresh authoritative snapshot; no auto retry/apply.

## Cycle 4 — Failure and privacy

External services and API credentials are explicitly blocked pending separate provider/privacy/rights/security and owner decisions. Build a real offline adapter with clear unsupported status for remote candidates, no stub pretending live. Treat model responses/evidence as untrusted data, never execute instructions/HTML/scripts or fetch links. No web requests by enrichment flow. Strict pre-read byte caps, fatal UTF-8, depth/array/text limits before expensive parsing/validation where feasible, bounded issue summaries, no partial activation. Use project-owned synthetic exact fixtures; dynamic responses should be generated deterministically from task within controlled synthetic mode, not arbitrary self-declared provider output. Real input not allowed. Every selected field and record explicit in task scope; review compares actual payload; task mutation/digest/revision drift invalidates response and proposal. Protect against replay, tampering, extra response slots, wrong target, duplicate suggestions, source claims unsupported, inconsistent evidence, source not allowlisted, cancel/read race, stale commit, unmount. Existing gateway atomicity and integrity tests remain. No backup contains unapproved task context; authorized expression remains ordinary library record. No new schema or lock.

## Cycle 5 — Efficiency and delivery

Choose conservative provisional limits: <=50 selected expressions/concepts per task, <=3 preassigned reviewer slots, <=100 suggestions per response, <=250 total proposal operations (or lower existing WP03 limit), 256 KiB per packet/response pre/post-read, 4,096 UTF-16 per rationale/evidence text, 512 UTF-16 suggested form, <=32 evidence references per response, JSON depth <=16 and total decoded chars <=200k; refine downward if needed, never increase existing limits. Explicit errors and no silent clipping; paginate UI, bound maps and comparison, no quadratic reviewer comparisons across unbounded input. No actual API cost or usage claims, no new dependency or background jobs. User-mediated workflow reduces network/credential complexity; real service enablement is later separately qualified. Add only needed routes/navigation; no empty services.

## Cycle 6 — Challenge and reconcile

Does the exported packet leak unrelated data? Can stale response target another concept? Is model agreement presented as truth? Does source license imply legal rights? Is external output blindly trusted? Does evidence survive as fake canonical provenance? Are synthetic simulations labeled? Can a user circumvent no-real-data policy? Can an approved operation be replayed without duplicates? Does a stale commit refresh while preserving valid changes? Acceptance covers these. Preserve WP01–WP03, test real UI and privacy/recovery, independent native CI. If meaningful actual provider or durable evidence requires material policy/schema change, record blocked scope instead of inventing support. G4/G5/G6 remain unchanged.
