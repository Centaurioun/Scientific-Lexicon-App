Concrete source finding at the pinned checkpoint: shouldHandleExternalRevision returns false whenever any batch is in flight. The subscription callback drops the revision notification; a conflict/rejection/error path does not necessarily reload a fresh snapshot. An applied/replayed transaction reloads the snapshot, but a notification received during that awaited reload can also be discarded. The callback carries a revision number; it is not an origin-authenticated batch ID. The current Dexie repository listeners are instance-local, not proof of cross-tab broadcast. Do not claim cross-tab delivery or invent a new cross-tab synchronization architecture. Test same-instance notifications and use real same-origin IndexedDB concurrent transactions where relevant to verify CAS/conflict and post-settlement freshness.

1. A different revision notification while a commit is pending, followed by conflict/stale/rejected/error settlement: the latest authoritative snapshot must become visible, stale proposals must not be actionable, and matcher state must be invalidated appropriately.
2. Notification during post-commit snapshot loading; reconcile without losing the later revision, stale load overwrite, infinite refresh loop or stuck loading/analysis.
3. Own successful commit/replay: preserve legitimate committed transaction, accurate notice and retained-run association only if the active context/run still matches. Do not discard newer proposals or their retention metadata indiscriminately. If a newer proposal is genuinely stale against a new revision, explicitly invalidate it.
